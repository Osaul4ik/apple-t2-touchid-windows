# Чому скан не відбувається — розбір по логах

## Коротка відповідь (актуально станом на другий hardware-запуск)

Сенсор **бачить палець, але жодного разу не робить знімок**. Це видно
одразу у двох незалежних логах з реального заліза — до і після
виправлення розміру payload команди StartMatch. Порівняння з macOS-логом
того самого ноутбука (та сама прошивка `23P5067`, той самий uid 501, ті
самі 3 identity) показує: на Windows у потоці подій немає жодного статусу
з image-конвеєра (`55 ImageCaptured`, `72 ImageForProcessing`,
`95 ImageWasAccepted`) і жодної статистики типів 0/1/2 (оцінки якості
знімка).

macOS при вдалому розблокуванні:

```
90 SensorOperationModeCapture
63 FingerOn
55 ImageCaptured          <-- ось сам скан
72 ImageForProcessing
95 ImageWasAccepted  (238 B)
91 SensorOperationModePause
64 FingerOff
...
>>> 0xE3FF8002 match_result, 3228 B <<<
73 TemplateListUpdated (3202 B)
```

Windows (обидва прогони, до і після фіксу StartMatch, ідентично):

```
90 SensorOperationModeCapture
statistics type 4, 35, 25
81   <-- такого коду немає в жодному вдалому циклі на macOS, спрацьовує ДО дотику
63 FingerOn
91 SensorOperationModePause
78   <-- такого коду теж немає, спрацьовує через ~1.5с після паузи
64 FingerOff
statistics type 30
90 SensorOperationModeCapture   <-- цикл повторюється
```

## Що точно НЕ зламано

- Транспорт, BridgeXPC, HELO, версії — ок.
- Парсинг подій — офсети (`embedded_type` на 8, ordinal на 24, довжина на 32,
  дані з 40) збігаються з тим, що показує сам Apple-івський демон.
- Identity list — 3 записи по 20 байт, і UUID, який macOS повертає при
  вдалому матчі (`D6AE7EAA-…`), — другий запис із твого ж списку. Шаблони на
  місці й доступні.
- `kMinMatchResultEventBytes = 0xC70` — коректний поріг.

## Перша спроба фіксу: розмір payload StartMatch (132 B → 68 B)

macOS на цій машині з тими самими 3 identity шле `inSize=68` для команди 4
(`68 == 8 + 3*20`). Проєкт раніше збирав `MatchInitDataV1(68) + uint32
count(4) + 3*20 = 132` байти. Виправив на `MatchIdentityLayout::
InlineIdentities` — 8-байтовий заголовок (`flags|uid`), одразу за яким
ідуть записи identity без лічильника — це й дає рівно 68 байт.

**Результат другого hardware-прогону з цим фіксом: поведінка на дроті не
змінилась ані на біт.** Той самий цикл `81 → 63 FingerOn → 91 → 78 → 64
FingerOff`, та сама статистика, жодного `55/72/95`. Лог підтверджує, що фікс
застосувався коректно (`layout=inline payload=68B`, `inner=76B` = 8+68), але
на симптом це не вплинуло.

**Висновок:** вміст/розмір payload StartMatch — не та причина, що блокує
сканування. Фікс лишається правильним (відповідає macOS-байтам), але сам по
собі проблему не вирішує. Причина ще вища за рівнем.

## Новий провідний кандидат: LoadCalibration

macOS у живому IPC-трафіку (`biometrickitd`) її не шле ніколи за 4 хвилини
активності з двома вдалими розблокуваннями. Але це не доводить, що вона не
потрібна — на macOS сенсор, ймовірно, калібрується один раз під час
завантаження самої ОС, ще до старту `biometrickitd`, тобто цей крок просто
не потрапляє в лог, який ми аналізували.

Якщо Windows завантажується через Boot Camp без проміжного завантаження
macOS у тому ж циклі живлення, цей крок калібрування може взагалі не
відбутися — сенсор лишається «озброєним, але не відкаліброваним»: механічно
(ємнісно) детектує палець (звідси `63 FingerOn`/`64 FingerOff` — апаратний
рівень, працює завжди), але не може зняти придатне зображення (image-рівень,
де все й ламається).

Додаткова опора для цієї гіпотези: коди `81` і `78` спостережені **двічі
поспіль з абсолютно тим самим паттерном**: `81` завжди до `63 FingerOn`
(автономний, не прив'язаний до дотику), `78` — завжди через ~1.5 с після
паузи. Консистентність між двома незалежними прогонами (з різним payload
StartMatch!) виключає випадковість і вказує на щось системне в самому
сенсорі, а не в наших командах матчу.

## Що змінено цього разу

| Файл | Зміна |
|---|---|
| `protocol/BiometricKit/VerificationEngine.cpp` | Рахує `fingerTouchCycles` (кількість `63 FingerOn`). Якщо ≥2 цикли без жодної image-pipeline події і `LoadCalibration` вимкнена — окрема лог-лінія з рекомендацією ввімкнути калібрування. `session summary` тепер включає `layout=`, `reset_sensor=`, `load_calibration=`. |
| `tools/t2touchid/main.cpp` | `verify-no-image` тепер прямо каже, що зміна layout-у нічого не дала на апаратному A/B-тесті, і першим кроком пропонує `--load-calibration`. |
| `tools/analyze-verify-log.py` | Гістограма статус-кодів; явний висновок «спробуй --load-calibration», коли ≥2 циклів без зображення. |
| `docs/macos-verified-status-map.md` | Розділ 7 — повний опис другого hardware-захоплення: чому фікс StartMatch не допоміг і чому LoadCalibration тепер пріоритетна гіпотеза. |

Раніше зроблене (`MatchIdentityLayout`, `StatusCodeName`, `NoImageCaptured`,
`ParseStatisticsEventBody` тощо) лишається без змін і досі коректне — просто
виявилось недостатнім самостійно.

## Наступний крок перевірки

```
t2touchid.exe verify -v --load-calibration
```

Якщо знову `verify-no-image` — далі `--match-layout padded` (друге можливе
прочитання тих самих 68 байт: тільки опції, без identity inline).

Після кожного прогону:
```
python3 tools/analyze-verify-log.py t2touchid-verify.log
```
Скрипт одразу скаже, чи з'явився `55 ImageCaptured` і чи з'явилась
статистика типів 0/1/2 — це і буде ознакою, що image-конвеєр нарешті
запрацював.

## Чесна межа впевненості

Розмір 68 vs 132 — факт із логу, тут сумнівів немає, і другий hardware-тест
підтвердив, що фікс застосувався правильно, хоча симптом не вирішив.
LoadCalibration-гіпотеза обґрунтована (macOS її не шле в IPC + консистентний
паттерн 81/78 на двох незалежних прогонах), але поки не доведена —
єдиний спосіб перевірити це на цьому залізі.

Коди `78` і `81` лишаються без імені навмисно: у жодному вдалому циклі
macOS вони не зустрічаються, тож придумувати їм значення не було на чому —
навіть після двох прогонів з різною поведінкою команд.
